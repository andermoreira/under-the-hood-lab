# C02 — Anatomia de um executável ELF

**Questão:** por que um ELF tem seções e segmentos, e qual deles o kernel usa para carregar o programa?

## Previsão (LEARN)

Antes de executar, registre sua hipótese: qual é a diferença entre `.text`, `.rodata` e `.data`? Todos os bytes de `.bss` ocupam espaço no arquivo? Qual é o entry point? O kernel precisa de uma tabela de seções para carregar um executável ELF?

## Experimento

Execute em Linux x86-64 com GNU binutils e Python 3:

```sh
make -C labs/low-level/C02 test
make -C labs/low-level/C02 inspect
```

O exemplo possui código (`.text`), string constante (`.rodata`), contador inicializado (`.data`) e buffer zerado (`.bss`). A implementação chama `write` e `exit` via ABI Linux x86-64. O script testa stdout, exit code, entry point, seções e segmentos carregáveis.

### Investigue

1. Compare `readelf -S` (seções, relevantes para ferramentas/linker) com `readelf -l` (program headers, usados pelo carregador).
2. Observe `p_filesz` e `p_memsz` nos segmentos `PT_LOAD`; explique por que `p_memsz` pode ser maior.
3. Use `readelf -h` para localizar `Entry point address` e `readelf -s` para localizar `_start`.
4. Compare `objdump -d` com o fonte. Identifique os endereços e os dois `syscall`.
5. **Falha controlada:** em cópia descartável, altere o entry point do linker para um símbolo inexistente e observe o aviso/resultado; não trate comportamento acidental como garantia. Refaça o build limpo.

## Critérios e limitações

- ENG: testes funcionais e inspeção estrutural passam em Linux x86-64 com GNU binutils.
- LEARN: previsão, evidências, divergências e ligação com B09 registradas no diário.
- Não confundir ELF64 com compatibilidade de ABI. O loader B09 é próprio; não implica suporte à ABI Linux nem aos mesmos layouts.
- Os layouts concretos dependem da versão do linker e de suas opções. O teste evita assumir endereços fixos ou quantidade exata de segmentos.
