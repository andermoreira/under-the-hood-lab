# C05 — ABI System V AMD64: C conversa com Assembly

**Pergunta central:** como duas linguagens concordam sobre argumentos, retorno, stack e registradores preservados?

## Preveja antes de executar

1. Quais registradores recebem os primeiros seis argumentos inteiros?
2. Onde o sétimo argumento fica no início de uma função chamada por C?
3. Por que a stack deve estar alinhada a 16 bytes **antes** de uma instrução `call`?
4. Quais registradores o callee deve preservar? Por que `rbx` é salvo no exemplo?

## Execute

Requisitos: Linux x86-64, GCC, binutils, Python 3.

```sh
make -C labs/low-level/C05 test
make -C labs/low-level/C05 inspect
```

Em `abi.s`, `sum_seven` recebe sete argumentos do C e soma todos. `call_callback` recebe um ponteiro de função e um inteiro, chama uma função C e devolve o resultado. Compare a stack na entrada de `call_callback` com a stack imediatamente antes de `call *%rbx`.

## Experimento de falha (em cópia descartável)

Remova `push %rbx` e `pop %rbx` e observe que o exemplo pode continuar aparentemente funcionando: testes funcionais **não provam** preservação de registradores. Use GDB ou um teste de ABI que force um valor vivo em `rbx` para detectar a violação. Depois restaure a implementação. Não confunda comportamento ocasional com contrato válido.

Compare `objdump -d` com o código-fonte; registre onde o compilador passa os argumentos. Alterne `-O0`/`-O2` e registre diferenças sem assumir endereços estáveis.

## Pontes e limites

- Este laboratório usa **ABI System V AMD64 para chamadas de funções**, diferente da convenção de argumentos das **syscalls Linux** (C03).
- O kernel próprio da Trilha B não implementa automaticamente essa ABI de usuário.
- Não cobre argumentos de ponto flutuante, variádicos, red zone, unwind completo, PIE ou todas as regras de classificação de agregados.

**ENG:** compilação com warnings como erros, teste funcional e inspeção de símbolos. **LEARN:** hipóteses, evidências e análise de falha registradas.
